# html-generator 技术手册

**版本：v1.13.1**

面向维护者与二次开发者。只想使用技能请看《用户手册》。

## 1. 架构总览

```
                        ┌─────────────────────────┐
   用户需求 ───────────▶│  SKILL.md（LLM 执行流程） │
                        └───────────┬─────────────┘
                                    │ 强制 Read
                    ┌───────────────┼───────────────┐
                    ▼               ▼               ▼
        references/semantic   references/      references/skeletons/
        -classes.md           palettes.json    mode-*.html
        design-system.md      chart-guide.md
                    │               │               │
                    └───────────────┼───────────────┘
                                    ▼
                        ┌─────────────────────────┐
                        │   生成的 HTML（源文件）   │
                        └───────────┬─────────────┘
                                    │
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
     chart_validator.py     impact_analyzer.py     convert.ps1 / .sh
     （数学校验，只读）        （降级分析）          （格式转换）
                                                          │
                                    ┌─────────────────────┼─────────────────┐
                                    ▼                     ▼                 ▼
                            html2docx.py          html2pdf.py        html2md.py
                            （四层拆分）           （Playwright）     （语义归约）
```

**核心设计：生成放开、转换归约。**

生成端刻意不设固定块模板——LLM 想怎么设计 HTML 都行。转换端靠「语义 class + 结构特征」把自由 HTML 归约到 25 种 IR 语义，再映射到目标格式。

好处：视觉自由度不设上限；代价：转换是"尽力而为"的语义归约，不是像素级还原。

## 2. 生成端

### 2.1 三阶段工作流

| Phase | 做什么 | 是否询问用户 |
|---|---|---|
| 1 意图分析 | 选模式（7 选 1）、选调色板（8 选 1）、定图片策略 | 否，自动判断 |
| 2 生成 HTML | 按骨架 + 语义 class 生成；图表坐标程序计算 | 否 |
| 3 格式转换 | 影响分析 → 确认 → 执行 | 是（有降级时） |

### 2.2 语义 class 体系

**12 种块级**：`title` `heading` `paragraph` `card` `table` `timeline` `stat` `code` `callout` `image` `list` `end_page`
**2 种辅助**：`cite`（正文内联引用标记）、`source-list`（来源列表容器）

规则：
- 只加在**关键结构最外层**
- 同一 class 可有完全不同的视觉呈现
- 未加 class 的元素，转换器兜底为普通段落（内容不丢，语义丢失）

可选 `data-*`：`data-level` `data-variant` `data-cols` `data-lang` `data-caption` `data-float` `data-layout`（Flex/Grid 布局意图标注）

### 2.3 生成端硬约束

| 约束 | 原因 |
|---|---|
| 零 JS（默认） | 保证离线自包含 + 转换保真 |
| 不引用外部 CSS/JS/图片/字体 | 同上 |
| div 嵌套 ≤ 5 层 | 转换时结构可控 |
| 文件名必须中文 | 交付可读性 |
| 骨架占位符必须替换为真实色值 | 未替换会导致浏览器无法解析 CSS |
| 图表坐标必须程序计算 | 手写坐标必然与数据不符 |
| 禁止手写转换脚本 | 见 §5.4 |

## 3. 图表子系统

这是本技能最复杂的部分：**37 种图表类型**，每种都有坐标公式 + Python 片段 + HTML 模板 + 校验函数。

### 3.1 三层保障

```
生成（Python 算坐标）
   ↓
数学校验（chart_validator.py）—— 数据点数 / 角度和 / 坐标越界 / 面积比 / 统计量序关系
   ↓
视觉核对（Playwright 截图 + 肉眼看）—— 抓脚本查不出的形状错误
```

**为什么需要第三层**：实测中数学校验全 PASS，但截图发现
- 瀑布图减量柱被画成增量色（颜色判断用了 `top > bottom`，负向柱也满足）
- 小提琴图画成锯齿菱形（小样本分箱直方图噪声太大）
- 堆叠柱状图 absolute 模式三根柱等高（百分比高度父级不确定，回退按内容计算）

这类问题公式层查不出，只能靠视觉。

### 3.2 类型识别：显式标记优先于启发式

早期用纯启发式识别图元，多类型共存时必然冲突：

- 玫瑰图各扇区半径不同 → 被饼图校验器判为"坐标不连续"
- 桑基图的 `M...C...` path（无 L 无 fill）→ 被折线校验器判为"只有 1 个点"

**解决**：引入 `data-chart="..."` 显式标记（22 种），并给 5 个旧校验器加守卫 `_explicit_type_mismatch()`——**带显式标记且不匹配时直接跳过，不再走启发式**。

> 教训：启发式类型识别在多类型共存的系统中不可扩展，必须让显式声明优先。

### 3.3 校验函数清单（36 个）

| 类别 | 函数 |
|---|---|
| 基础 | `validate_pie` `validate_barchart` `validate_linechart` `validate_areachart` `validate_radar` `validate_scatter` |
| SVG 扩展 | `validate_bubble` `validate_gauge` `validate_waterfall` `validate_rose` `validate_treemap` `validate_candlestick` `validate_quadrant` `validate_errorbar` `validate_violin` `validate_streamgraph` `validate_range_area` `validate_step_line` `validate_slope` `validate_stacked_area` `validate_sankey` `validate_boxplot` |
| DOM 型 | `validate_stacked_bar` `validate_rank_bar` `validate_histogram` `validate_diverging_bar` `validate_pyramid` `validate_funnel` `validate_combo` `validate_pareto` `validate_bullet` `validate_wordcloud` `validate_sparkline` |
| 表格型 | `validate_heatmap` `validate_calendar_heatmap` |
| 兜底 | `validate_svg_generic` |

### 3.4 关键实现细节

**`parse_path_d`**：解析 `M/L/A/C/Q/Z`。早期只支持 `M/L/A/Z`，导致贝塞尔轮廓（小提琴、桑基）被当成"只有 1 个顶点"。

**`_in_viewbox`**：统一判断图元是否越界，所有 SVG 类型共用。

**`get_data_chart`**：读 `data-chart` 并 `strip().lower()`，兼容大小写与空格。

**`extract_chart_labels`**：按 `.chart-labels > span` → `.legend-item` → SVG `<text>` 顺序取标签，用于"图元数 = 标签数"比对。

## 4. 转换端

### 4.1 四层拆分架构（Word）

```
sem_common.py        公共语义识别层（三份脚本共用）
    ↓
docx_utils.py        Word OXML 工具层（字体 / 调色板 / OXML 操作）
    ↓
处理层（四层）        core（封面/标题/段落/列表/表格/图片）
                     enhanced（指标卡/callout/时间线/代码块）
                     scene（卡片网格/分隔线/Tab组/折叠组/Hero）
                     advanced（引用/多栏/对比卡/FAQ/画廊/尾页）
    ↓
html2docx.py         主入口 + 分发器
```

`html2md.py` 与 `impact_analyzer.py` 复用 `sem_common.py` 的同一份语义识别逻辑，保证三份脚本对"这是什么块"的判断一致。

`html2pdf.py` 独立无依赖（Playwright 无头 Chromium）。

### 4.2 内置兜底机制

| 场景 | 兜底 |
|---|---|
| 未知图表容器（含 svg/canvas） | 三层降级：① Playwright 截图插 PNG ② 提取 SVG 文本重建表格 ③ 跳过 |
| 无文本容器（纯图片/SVG）被跳过 | `flatten_semantic_blocks` 增加媒体子元素检测 |
| 封面/尾页行高不匹配 | 动态计算行高，兜底 20cm |
| 尾部空白页 | 清理孤立空段落、压缩必需段落到 1pt |
| 格式健康 | 修正超宽表格、缩小超大图片、删除全空表格 |

### 4.3 环境管理

`convert.ps1` 优先用 conda env `html-convert`；创建失败时写 `.conda_create_failed` 标记并回退 venv（`~/.html-convert-env`），后续直接走 venv 不再等待。

## 5. 质量保障体系

### 5.1 三视角对抗性审查

| 视角 | 关注什么 | 手段 |
|---|---|---|
| 工具实现者 | 边界、异常、崩溃 | 27 个 fuzz 用例（空文件/缺属性/非法值/除零/嵌套/极端值/中文） |
| 审查者 | 文档 ↔ 实现漂移 | 一致性脚本：标记 ↔ 校验函数 ↔ 模板 ↔ SKILL.md 计数 四方核对 |
| AI 使用方 | 指令可执行性 | 必读清单完整性、类型名一致性、模板可复制性 |

**审查审查工具**：三个审计脚本自身也出过 bug（正则用半角 `)` 但实际是全角 `）`、split 后未 strip 空格、假设 palettes.json 结构与实际不符），都已修正。**审计工具必须先验证自身**。

### 5.2 清单约束兜底（selfcheck.py）

把"文档 ↔ 实现漂移"固化为 7 大类可执行清单，发布前必跑：

1. 文件完整性（27 个必需文件）
2. 版本号一致性（VERSION / README / 两份手册）
3. 语义 class 体系（12+2 全部定义）
4. 调色板（8 组 × 20 色位）
5. 图表体系（类型数 / 校验函数注册 / 标记 / 模板 四方一致）
6. SKILL.md 指令可执行性（必读清单、硬约束）
7. 真机验证（校验器能检出注入错误、三种格式分析可用、依赖可导入）

### 5.3 真机验证

端到端跑通：HTML → Word（154KB，5 张图表 PNG）→ PDF（68KB）→ Markdown。

验证产出质量而非只看退出码——这一步发现了"Markdown 转换丢失全部 SVG 图表数据但不提醒"的缺陷，已通过在 `impact_analyzer.py` 增加图表专项提醒修复。

### 5.4 硬性禁令：禁止手写转换脚本

`html2docx_scene.py` 的 `process_collapse_group`、`html2docx_enhanced.py` 的 `process_stat_block` 等针对 25 种 IR 结构有专门处理。**曾发生绕过内置脚本手写转换、导致折叠卡片内 12 条招标项目详情全部丢失的事故。**

内置脚本报错时应排查调用方式（缺依赖、路径错），而不是自己写一个。

## 6. 扩展新图表类型（标准流程）

1. **写规范**：在 `references/chart-guide.md` 新增章节，含 ① 计算公式（Python）② 标准 HTML 模板 ③ 必备 CSS ④ 强制标记 ⑤ 校验要点
2. **写校验**：在 `scripts/chart_validator.py` 新增 `validate_xxx()`，并注册到 `validate()` 主流程
3. **登记标记**：把新 `data-chart` 值加入 `KNOWN_DATA_CHARTS`
4. **加守卫**：若新类型图元可能被旧校验器误判，给旧校验器加 `_explicit_type_mismatch` 守卫
5. **写 fixture**：生成含该类型的测试 HTML，跑校验确认 PASS
6. **对抗性测试**：注入一处错误，确认校验器能抓到
7. **视觉核对**：截图 + 肉眼看形状
8. **更新文档**：SKILL.md 规则 15/16 的类型数与列举、chart-guide 速查表
9. **跑自检**：`python scripts/selfcheck.py`，确认类型计数一致

> 第 4 步最容易漏。玫瑰图和桑基图都栽在这里。

## 7. 打包与发布

```bash
python scripts/build_release.py --bump patch    # 或 minor / major
```

流程：

1. 读 `VERSION` → 递增 → 写回
2. **自动重命名两份手册**为 `用户手册_vX.Y.Z.md` / `技术手册_vX.Y.Z.md`，并替换文内版本号
3. 替换 `README.md` 中的版本号
4. 跑 `selfcheck.py`（有 ERROR 则中止）
5. 打 zip 到 `dist/html-generator-vX.Y.Z.zip`

手册文件名的版本号由脚本维护，**不要手改**。

## 8. 已知限制

| 限制 | 影响 | 规避 |
|---|---|---|
| 转 Markdown 丢失 SVG 图表数据 | 图表只剩文本标签 | 需保留图表时用 HTML/Word/PDF；影响分析已提醒 |
| 行内多 span 转 Markdown 会粘连 | 如 "49%33%18%Q1" | 影响分析已提醒 |
| 交互组件转 Word/PDF/MD 丢失 | Tab 全展开、折叠全展开 | 影响分析已提醒 |
| 未装 Pillow | 图片压缩失效（保留原图） | `pip install pillow` |
| 未装 pymupdf | PDF 尾页空白检测跳过（仅 WARN） | `pip install pymupdf` |
| 未装 cssutils | `<style>` 预解析跳过（可选增强） | `pip install cssutils` |
